Engineering

The quiet cost of clever abstractions

14 August 2026 / 12 minute read

There is a particular kind of pull request that feels wonderful to write and terrible to inherit. It collapses six similar functions into one configurable engine. It removes ninety lines. The diff is green in all the right places, and every reviewer leaves a small celebratory emoji.

Eighteen months later, someone is reading that engine at two in the morning, trying to work out why a single customer’s invoice renders with the wrong currency, and the answer lives four layers down in a branch that only fires when two configuration flags disagree.

The six duplicated functions would have been six greppable places to look. The abstraction turned them into one place you cannot read.

Duplication is cheaper than the wrong shape

The instinct to remove repetition is a good one, and it is also the most commonly misapplied rule in our field. Repetition is visible; the wrong abstraction is invisible until it fails. When you merge two things that merely look alike, you have not removed complexity — you have hidden the fact that they were never the same thing.

Prefer duplication over the wrong abstraction. It is far easier to fan a function back out than to untangle one that grew a personality.

My working rule is to wait for the third occurrence, and then to look at the reasons rather than the shapes. Two pieces of code that change for the same reason belong together. Two that happen to have the same five lines today do not.

A test you can run in your head

Before extracting anything, I try to answer one question out loud: if the requirement changed for exactly one caller, how much of this would I have to undo? If the honest answer involves a new boolean parameter, the abstraction is already failing, and it has not even shipped yet. 

// The boring version. It fits on a screen.
function invoiceTotal(lines, taxRate) {
  const subtotal = lines.reduce((sum, l) => sum + l.amount, 0);
  return subtotal + subtotal * taxRate;
}
Boring code has a useful property: you can hold all of it in your head at once, which is the only kind of verification that happens at 2am.

What to do instead

  • Write the direct version first, even if it repeats.
  • Name the reason two things are the same, not the syntax.
  • Let the third example tell you the real shape.
  • When you do abstract, make the seams easy to cut again.

None of this is an argument for sloppiness. It is an argument for paying the cost of an abstraction only once you know what you are buying — and for remembering that the person who pays it is usually not the person who wrote it.
